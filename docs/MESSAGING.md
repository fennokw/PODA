# Messaging and remote requests

Messaging and notifications are opt-in. In Messages choose Apple Messages or GroupMe, search for conversations, add them, and enable reading and/or sending; or explicitly grant access to all conversations. Sending uses your signed-in account. Contact names are read through macOS Contacts when permission is granted. Apple Messages requires macOS Full Disk Access for reading and Automation permission for sending. GroupMe uses its own servers and an access token stored in Keychain. WhatsApp and Instagram are not connected.

Under “Talk to PODA in a conversation,” search for a conversation that has both reading and sending access, choose a prefix such as `/PODA`, choose allowed senders and capabilities, and confirm. You can add multiple monitored conversations with different settings. `self` allows messages sent by your own account; add exact phone numbers or email addresses for other Apple Messages participants, or GroupMe user IDs for GroupMe. Only messages whose first token is the selected prefix are processed. An allowed participant can trigger every enabled capability: the prefix is not a password, and chat participants can see requests and replies. PODA replies from your account beginning `[PODA]:`. Stop monitoring at any time; removing read/send permission also stops processing. Previously configured key-based remote mode remains separately revocable; adding the same conversation to the new mode turns off the legacy monitor for that conversation.

General questions are answered using the local model. Notion agenda reading and calendar creation are separately selectable. Coding allows reading and editing only inside the explicitly selected, existing edit-granted folder, subject to the underlying file permissions; it does not authorize execution of code or tests. Do not enable actions for senders you do not trust. Interrupted or older-than-ten-minutes requests are not replayed. Be aware that phone numbers and provider sender identifiers are not cryptographic authentication.

Under Text notifications choose an allowed sending conversation, coding-response alerts and/or timed Notion event reminders, lead time and IANA time zone. Coding alerts mean a response finished generating, not that work is verified. Reminders exclude all-day entries and deadlines, are best effort, and are not replayed after downtime. Event titles are visible to conversation participants and the provider. Notifications can be disabled independently.

A daily automation can send its completed response to one explicitly approved conversation. Under Daily Automation enable “Send the completed update by message” and select a conversation that already has sending permission. Each run records its delivery status in its history. Failed runs are not sent; updates are limited to five messages, with a notice when shortened. Uncertain sends are not retried automatically. Pausing or editing the schedule, revoking conversation access, or turning on Offline Mode blocks later sends.

While the Mac desktop app is open it prevents automatic idle system sleep while allowing the display to sleep. Closing its window leaves it running; Shut down PODA stops background work. A powered-off, manually sleeping, disconnected, or closed-lid Mac cannot reliably run PODA or send messages. Keep the computer powered, connected and awake.

Test macOS permissions, Contacts and Messages.app scripting and end-to-end behavior on the actual Mac and connected accounts before relying on these features. Synthetic automated tests do not verify real-world delivery.

Each monitored conversation now has an **Edit** button. Turn off **Require a code word** to process every new text from an allowed sender; existing monitors keep code words required by default. Messages beginning `[PODA]:` are always ignored, including mirrored self-chat replies and notifications. Identical command text mirrored within five seconds in the same conversation is processed once.

Calendar creation and **editing existing calendar events** are separate permissions. Existing creation grants are preserved; editing requires explicit opt-in and verified Notion update access. The remote planner receives the chat's authorized tool list and current local clock, and retries once if it answers an action request without trying a tool. Calendar replies report actual execution receipts rather than asking another model to invent a success or permission explanation. Weekly series use individual verified event creations; only reported operations should be treated as completed. The existing Notion tool accepts future starts within 90 days.
